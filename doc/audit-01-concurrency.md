# 审计报告 01 — 并发 / 限流 / 重试子系统

> 审计日期：2026-07-28 ｜ 审计对象：`oldCode/CoTBuilder-V2.py`
> 审计人：Claude ｜ 结论：**原始设计意图清晰且合理，但实现使两个核心指标（并发上限、QPM 上限）一个完全失效、一个被重试放大稀释，且缺乏任何可观测手段**

---

## 1. 原始设计初衷还原

从参数命名、docstring 与注释可以明确还原出设计者的意图，其设计本身是**正确的**：

| 设计意图 | 代码证据 |
|---|---|
| **双维度独立限流**：QPM ≤ 50（保护 API 配额）且同时在途请求 ≤ 10（保护连接/内存资源） | 构造函数参数 `qpm_limit=50, max_concurrent=10`（`CoTBuilder-V2.py:193-194`） |
| **按错误类别分离重试预算**：网络错误 → 指数退避免费重试；质量不匹配（MISMATCH）→ 消耗 `max_retries` 的有限重试 | `_network_retry_call` docstring「不消耗重试次数」（`:300`）；`max_retries` 参数注释「仅用于 MISMATCH」（`:202`） |
| **MISMATCH 三并发抽卡**：一次并发采 3 个样本，取匹配度最高者 | 「MISMATCH，启动三并发抽卡」（`:573`） |
| **实时落盘 + 断点恢复**：每样本完成即写盘，崩溃后可续跑 | `RobustFileWriter`（`:46-122`） |

一句话概括设计目标：**在严格不越过 QPM 配额的前提下，用满允许的并发度，让吞吐贴着配额走；重试按错误类别各归各的预算，互不影响。**

## 2. 实际行为分析

### 2.1【致命】并发上限完全失效 —— 信号量守错了地方

`qpm_semaphore = Semaphore(max_concurrent)`（`:220`）在 `_rate_limit()` 内通过 `async with` 获取（`:243`），在时间戳追加后随 `with` 块结束而释放（`:293`）—— **释放发生在发起 HTTP 请求（`:316`）之前**。

后果：

- 该信号量实际只串行化了「限流检查」这一纯内存操作（微秒级），对真正需要限制的「在途 HTTP 请求」**没有任何约束**；
- `generate_batch` 一次性为全部样本创建协程（`:696-706`），在途协程数 = 样本总数。跑 1000 个样本就有 1000 个协程同时存活，通过闸门后即同时挂起在 HTTP 请求上；
- 设计意图中的 `max_concurrent=10` **从未被实现过**。在途请求数完全由 QPM 闸门放行速率与请求延迟自然决定（稳态约 50 个），且无任何硬上限。

**这是整个子系统最核心的缺陷：两个限流维度被融合进一个信号量，而这个信号量两个维度都没守住 —— 并发维度完全失守，QPM 维度只靠巧合式的串行化勉强守住（见 2.2）。**

### 2.2 QPM 闸门：碰巧能用，但建立在脆弱的基础上

限流检查在时间戳双端队列上做滑动窗口（`:241-297`）。由于检查全程持有信号量，同一时刻只有一个协程能清理/检查/追加时间戳 —— 恰恰是这个「副作用串行化」让窗口统计本身是一致的，**请求发起速率确实被限制在 50 次/60s 以内**。

但这是碰巧正确，而非设计正确：

- 窗口逻辑、等待逻辑、并发控制全缠在一个函数里，任何人改动其中一处（例如把信号量移到正确位置）都会无声地打破 QPM 统计的一致性；
- 等待窗口滑动时**持有信号量睡眠**（`:273-290`），形成队头阻塞：一个协程睡 1 秒，其余 9 个槽位的协程连「检查自己是否该等」都做不到。虽然稳态下放行速率不变，但等待被强行串行化，徒增延迟方差；
- 客户端按「发起时刻」记账，服务端按「到达时刻」计数。闸门放行后的突发（瞬时 50 个请求同时发出）在服务端固定窗口口径下仍可能触发 403 —— 触发的 403 又会进入 2.3 的重试放大。

### 2.3【致命】重试放大无上限，且与正常流量抢同一本账

单个样本的请求链路：

```
首次调用 _network_retry_call          → 最多 5 次 HTTP 请求（指数退避）
  └─ MISMATCH → 3 路并发抽卡           → 每路又是一个 _network_retry_call
                                          → 每路最多再 5 次
单样本最坏情况：5 + 3×5 = 20 次 HTTP 请求
```

而**每一次请求都会进入 `_rate_limit()` 消耗 QPM 配额**（`:313`）。后果：

- 设计预算是「50 QPM 全部用于推进新样本」，实际是重试和抽卡与新样本**抢同一本账**，且没有任何一方有优先级或上限。错误率/不匹配率稍高时，有效吞吐（新样本推进速率）会远低于配额，且无法预测；
- `max_retries` 参数声明后**从未被引用**（全文仅 `:209` 赋值一次），「MISMATCH 消耗重试次数」的设计意图没有实现，取而代之的是固定 3 并发抽卡；
- 结果字段 `"attempts": 1` 全部硬编码（`:560, :612, :630, :647`），重试统计完全失真，线上连「放大到底有多严重」都无从得知。

### 2.4 403 识别粗放，被限流还要倒贴配额

- 403 是否属于 QPM 限流靠在错误文本里搜 `"qpm"` / `"频率"` 子串判断（`:339`），服务端文案一变即失效；非 QPM 类 403（如鉴权）走 `API_ERROR` 不重试，尚可接受，但分类依据同样脆弱；
- 每次被 403 拒绝的请求**已经在本地时间戳队列里记过账** —— 被服务端限流不仅浪费一次往返，还倒贴一份本地配额，退避后重试再记一份，双重损耗。

### 2.5 每次请求新建 ClientSession

`_network_retry_call` 每次尝试都 `aiohttp.ClientSession()`（`:315`）：

- 无连接复用，每个请求一次完整 TCP+TLS 握手，在 30–90s 延迟本就敏感的链路上白白增加秒级开销与 fd 占用；
- 配合 2.1 的无界并发，瞬时可能同时存在数十上百个 session，加剧内存与 fd 压力（每条消息还内嵌 base64 图片）。

### 2.6 无任何可观测性

全系统没有一处统计：当前在途请求数、过去 60s 实际发起请求数、单样本请求放大倍数、QPM 配额中多少被重试消耗。**系统偏离设计预期时，没有任何信号能暴露偏差** —— 这正是「效果很差但说不清哪里差」的直接原因。

## 3. 设计意图 vs 实际行为对照

| 维度 | 设计意图 | 实际行为 | 后果 |
|---|---|---|---|
| 并发上限 | 在途 ≤ 10 | **无上限**（= 样本数） | fd/内存压力，连接抖动 |
| QPM 上限 | 发起速率 ≤ 50/min | 碰巧成立（靠检查串行化） | 脆弱，任何人重构都可能打破 |
| 网络重试 | 免费、退避、有界（5 次） | ✅ 基本实现 | 但与抽卡叠乘后放大至 20× |
| MISMATCH 重试 | 消耗 `max_retries` | **未实现**，固定 3 并发 | 预算概念丢失 |
| 配额账本 | 服务于新样本推进 | 新样本/重试/抽卡混记一本账 | 有效吞吐不可预测 |
| 重试统计 | 真实 attempts | 硬编码 1 | 无法观测放大 |
| 连接管理 | （未明示，隐含复用） | 每请求新建 session | 延迟与资源双重浪费 |

## 4. 量化估算（基于 mock 建模参数：单请求延迟 30–90s）

- 按 Little's Law：平均延迟 60s 时，打满 QPM 50 需要约 **50 个在途请求**；若并发上限真按设计的 10 实现，吞吐天花板约 **10 QPM** —— 说明设计参数本身（QPM 50 × 并发 10）就不自洽，重构时两个参数的关系需要在文档中讲清楚；
- 零错误理想情况下，老代码吞吐 ≈ 50 次发起/分钟（闸门碰巧正确）；
- 设 MISMATCH 率 30%、网络错误率 10% 的典型场景，重试与抽卡消耗的配额占比将显著抬升，**有效新样本吞吐可降至配额的 60–70% 以下**，且随错误率波动 —— 这解释了线上「效果差」的体感：配额花完了，样本没推进多少。

## 5. 重构方向（详细设计另立文档）

1. **三职责分离为三个独立组件**：
   - `RateLimiter`：纯「发起许可」闸门（滑动窗口或令牌桶），**不持有任何资源、不睡眠占用并发槽位**，等待期间只挂起协程自身；
   - 并发信号量：包裹**完整 HTTP 请求生命周期**（获取 → 请求 → 释放），而非包裹限流检查；
   - 重试策略：独立的退避函数，只负责「何时再试」，不感知限流与并发。
2. **正确的获取顺序**：先等 RateLimiter 放行（此时不持有任何资源），再获取并发槽位，再发请求 —— 杜绝「占着槽位睡觉」。
3. **请求预算显式化**：单样本请求上限（含全部重试与抽卡）作为配置项，真实 `attempts` 写入结果；配额消耗分账统计（新样本 / 重试 / 抽卡）。
4. **共享 ClientSession**：全生命周期一个 session，连接池复用。
5. **内建指标**：在途数、窗口内发起数、放大倍数、分账配额占比 —— mock 测试断言这些指标，而非只看最终成功率。

## 6. 结论

老代码的并发系统是一个「设计意图正确、实现全面走样」的典型案例：设计者想要的是两道独立的闸门（速率 × 并发）加两本分离的重试账，实现出来的却是一道守错位置的闸门加一本糊涂账。QPM 上限靠副作用碰巧守住、随时可能被下一次修改打破；并发上限从未存在；重试放大无界且不可观测。**重构的第一优先级（R1/P0）即为此模块，且必须以可断言的指标（而非行为感觉）验收。**

## 附录 A：线上观测现象的机理还原（2026-07-28 补充）

**观测现象**（来自线上实际运行）：系统在某些情况下 QPM 诡异地冲到 100 左右，随后全部请求一起卡死，之后陷入不停重试、零零散散完成的状态。

该现象可由本报告 §2 的缺陷完整解释，其因果链如下：

### A.1 第一步：冷启动突发（闸门只封顶、不匀速）

滑动窗口闸门只限制「任意 60s 内 ≤ 50 次发起」，**不限速、不间隔**。冷启动时窗口为空，前 50 个协程在秒级内连续通过闸门（检查是纯内存操作，微秒级），叠加 §2.1 的无界并发 —— **50 个请求几乎同一瞬间打向服务端**，而不是设计隐含的「每分钟匀速 50 个」。

### A.2 第二步：窗口口径错配，服务端看到 ~100 QPM

客户端按**滑动窗口**记账（任意 60s ≤ 50），服务端按**固定自然分钟窗口**计数（MaaS 网关常见实现）。滑动窗口在固定窗口边界处天然允许 2× 峰值：

```
分钟 N 末尾：发起 50 个（客户端窗口内合法）
分钟 N+1 开头：再发起 50 个（旧时间戳滑出，仍合法）
服务端视角：分钟 N 或 N+1 内到达 ≈ 100 个 → 触发 403 限流
```

**「冲到 100 左右」≈ 2 × qpm_limit，正是滑动/固定窗口错配的理论峰值。** 之后大量请求收到 403（错误文本含 "qpm"，命中 `:339` 的子串匹配）。

### A.3 第三步：同步退避 → 「全部一起卡死」

突发的 50 个请求在相近时刻收到 403，各自进入**完全相同**的指数退避表 `min(5·2^attempt, 60)s`（`:340`）—— 整个协程舰队在同一时刻集体入睡，在途请求清零，吞吐归零。从外部看就是「全部一起卡死」。

卡死被闸门进一步放大：本地窗口仍被第一步突发的 50 个时间戳占满，新任务进入 `_rate_limit()` 必须等旧时间戳滑出（最长 60s）；而等待**持有信号量**（§2.2 队头阻塞），最多 10 个在等、其余堵在获取信号量上 —— 整条管线彻底冻结。

### A.4 第四步：同步唤醒 → 振荡循环 → 「零零散散完成」

窗口滑出与退避结束在相近时刻发生，堵在闸门内的最多 10 个等待者 + 退避醒来的舰队**在同一两秒内集体醒来**，再次形成突发 → 再次触发服务端 403 → 再次同步退避。这是一个经典的**极限环振荡**（limit cycle）：

```
突发 → 403 风暴 → 同步退避（卡死）→ 同步唤醒 → 再突发 → …
```

唯一打破同步的是 30–90s 随机延迟带来的抖动：个别请求错峰滑过闸门成功 —— 表现为「零零散散完成」。同时每一轮振荡的重试都在消耗本地 QPM 配额（§2.3），有效吞吐被持续压制；5 次重试耗尽后以 `NETWORK_ERROR` 失败，而 `attempts` 硬编码为 1，**振荡期间留下了大量失败样本且无任何痕迹可查**。

### A.5 对重构的修正要求

该观测为本报告 §5 的重构方向追加两条硬性要求：

1. **限流器必须匀速放行（paced），而非仅封顶（capped）**：滑动窗口/令牌桶需带最小放行间隔（如 QPM 50 → 间隔 ≥ 1.2s），从源头消除突发，避免服务端固定窗口口径下的 2× 峰值；
2. **退避必须加抖动（jitter）**：指数退避时间乘随机因子（如 ±50%），破坏舰队同步，避免「同时入睡、同时醒来」的振荡结构；
3. mock 测试需新增场景：**「403 风暴 + 恢复」**，断言恢复过程中任意 1s 内的发起数不超过 `qpm_limit × (窗口换算值)` 的匀速上界，且系统在 N 秒内恢复稳态吞吐 —— 以此验证振荡不会复现。

## 附录 B：成功率负优化与十倍耗时的归因（2026-07-28 补充）

**观测数据**（来自线上实际运行）：

1. 串行/旧版最优成功率约 **30%**（注：其鲁棒性校验本身也有缺陷，30% 仅为参考基线）；而带错误并发实现的版本成功率不升反降，仅 **~10%** —— 并发抽卡产生了**负优化**；
2. 理论耗时：30 个样本 ≈ 30 次首次调用 + 最多 90 次抽卡 = **≤120 次请求**，按 QPM 50 匀速放行约 2.4 分钟 + 30–90s 延迟填充，**1–3 分钟应完成**；实际耗时约 **10 分钟**。

### B.1 成功率负优化的机制：抽卡制造了压死自己的风暴

抽卡（3 并发采样选最优）的设计目的是**提高**单样本匹配概率。但在本实现中它适得其反，因果链为：

```
MISMATCH → 3 倍请求放大（§2.3）
        → 请求突发更容易越过服务端固定窗口（附录 A.2）
        → 403 风暴
        → 风暴中每个 403 都会烧掉 _network_retry_call 的一次尝试额度（:311 循环共 5 次）
        → 首次调用与 3 路抽卡调用一起批量额度耗尽 → NETWORK_ERROR
        → 同窗口内其他无辜样本的调用也被波及（共享配额、共享退避时刻）
```

关键点：**抽卡放大的请求量正是触发风暴的直接原因，而风暴杀死的恰恰包括抽卡请求本身** —— 自我挫败（self-defeating）。叠加对同窗口其他样本的连带杀伤，并发版本整体成功率（~10%）跑输无抽卡/串行基线（30%）即「负优化」。

另一个隐性损耗：被 403 拒绝的请求已在本地窗口记过账（§2.4），其重试再记一笔 —— 风暴期间配额被大量消耗在「注定失败的请求」上，正常样本的调用反而排不到配额，进一步拉低成功率。

### B.2 十倍耗时的账本：请求数膨胀 × 有效速率崩塌

总耗时 ≈ 总请求数 ÷ 有效放行速率，**两个因子同时恶化，乘法叠加**：

| 因子 | 理论值 | 实际值 | 恶化机制 |
|---|---|---|---|
| 总请求数 | ≤120（30 首次 + 90 抽卡） | 估计 **300–600** | 成功率 10% → 27 个失败样本；每个失败样本在风暴中烧掉多次重试（单样本最坏 20 次，§2.3）；403 重试重复记账 |
| 有效放行速率 | 50/min | 估计 **20–30/min** | 振荡周期内的同步退避造成大段吞吐为零的死亡时间（附录 A.3）；配额被重试/抽卡挤占（§2.3） |
| **总耗时** | **1–3 min** | **~10 min** | 120/50 → 400/25，两个方向各 2–4 倍，相乘得 4–10 倍 |

即存在一个正反馈环：**失败 → 重试与抽卡产生更多请求 → 更容易触发风暴 → 更多失败**。系统在错误率稍高时不是线性退化，而是沿此环螺旋恶化。

### B.3 对 mock 测试的指标要求

以上两条观测转化为可断言的验收指标：

1. **请求数守恒**：给定样本集与 mock 的匹配概率，实际发出的 API 请求总数不得超过策略上界（首次 + 3×MISMATCH，重试走独立预算且单独计数）—— 拒绝任何隐性放大；
2. **时间包络**：30 样本 / 120 请求 / QPM 50 / 延迟 30–90s 的场景下（测试可用缩短延迟或虚拟时钟加速），墙钟耗时应落在 `请求数/QPM + 延迟填充` 的理论包络内（如 ≤ 1.5× 理论值）；
3. **并发不劣化成功率**：同一 mock 匹配概率下，并发管线成功率应与串行基线统计等价（允许采样噪声）—— 负优化不得复现；
4. **风暴期间预算隔离**：403 重试消耗独立的退避预算，不得烧掉样本级重试额度，不得挤占新样本的 QPM 配额分账。
