# 审计报告 02 — 鲁棒匹配与验收判定

> 审计日期：2026-07-28 ｜ 审计对象：`oldCode/CoTBuilder-V2.py` 中 `RobustMatcher`（`:129-182`）及 `SYSTEM_PROMPT_V2_3`（`:19-39`）
> 审计人：Claude ｜ 结论：**现有实现规格覆盖不足且多处超规格归一化（引入假阳性）；真正的验收判定器代码缺失，验收语义不可审计。重构时以本文 §4–§6 的需求规格为准**

## 1. 问题域与设计意图

原始多模态数据大量来自**单据、车票等复杂结构文档**，由标注与伪标签推理产出的 Ground Truth（GT）存在两类系统性问题：

1. **标注风格不统一**：同一信息在不同样本中全角/半角、中文/英文标点、标点后空格习惯各异 —— 这些是**格式噪声，不代表提取错误**；
2. **GT 本身未必可靠**：上游数据清洗与伪标签推理质量不佳，GT 中可能含真实错误 —— **MISMATCH 不等于模型错**。

这正是选择 CoT 方案的原因：让模型输出推理链，与 GT **交叉验证** —— 一致则互相印证，不一致则需区分「格式噪声」「模型真错」「GT 真错」三种情形。因此鲁棒匹配器的职责是双重的：

- **验收判定**：决定样本是否通过（产出可用 CoT 数据）；
- **诊断分析**：逐字段输出差异分类与聚合统计，反哺 GT 质量评估与 prompt 调优（「顺便分析一下处理的样本」）。

**归一化规格边界**（来自需求方，2026-07-28）：

| 应当解决（归一化后视为一致） | 不应当解决（视为真实差异，即 MISMATCH） |
|---|---|
| 全角 ↔ 半角符号（含中英文标点） | 大小写错误（如 `LAU` vs `Lau`） |
| 标点后空格有无（如 `LAU, LAI` vs `LAU,LAI`） | |

## 2. 现有代码审计（RobustMatcher，:129-182）

### 2.1 规格覆盖不足：全半角问题只解决了一小半

`punctuation_map` 仅含 `( ) ,` 三对映射（`:134-138`）：

- 缺失常见中英文标点对：`： ; ； ? ？ ! ！ " " ' ' 、 。` 等 —— 单据/车票中高频出现；
- **全角字母与数字完全未处理**：`Ａ-Ｚ ａ-ｚ ０-９`（U+FF01–FF5E 区段）在中文单据 OCR/标注中极为常见（如全角票号 `１２３４５`），属于规格第 1 条的核心场景，现有实现会直接判为 MISMATCH（假阴性）。

### 2.2 超规格归一化：删除全部空格（引入假阳性）

`normalize()` 中 `text.replace(" ", "")`（`:147`）删除值中的**所有**空格，而规格仅允许归一化「标点后的空格」：

- 反例：`"LAU, LAI LI"`（GT）vs `"LAU,LAIL I"`（模型输出）→ 归一化后均为 `LAU，LAILI`，判为 NORMALIZED_MATCH —— 但后者姓名拼写已被破坏，属真实错误；
- 英文/拼音字段（车票姓名、地址）中空格承载语义，全删会把「拼写错误」洗成「格式一致」。

### 2.3 超规格归一化：删除货币符号 ¥（引入假阳性，且漏掉真变体）

`text.replace("¥", "")`（`:150`）：

- **规格外**：符号缺失是真实提取错误 —— `SYSTEM_PROMPT_V2_3` 提取规则 3 明确要求保留货币符号（`:34`），模型漏输出 `¥` 应判 MISMATCH，而非洗成 NORMALIZED_MATCH；
- **漏真变体**：真正该归一化的是全角 `￥`（U+FFE5）↔ 半角 `¥`（U+00A5）这一对宽度变体，现有实现反而没有处理；
- 与提取规则自相矛盾：prompt 要求照抄，匹配器却原谅不照抄 —— 规则与验收口径不一致会让 prompt 调优失去反馈依据。

### 2.4 比较粒度过粗：整字典相等，无逐字段诊断

`classify_match()`（`:154-182`）对预测与 GT 做**整字典相等**比较：

- 一个字段不匹配即整体 MISMATCH，**无法回答「哪个字段、差在哪」** —— 交叉验证分析（§1 职责 2）无从谈起；
- 键缺失与键多余不加区分，均归入 MISMATCH，无法统计「模型漏字段」vs「GT 多字段」的模式（这正是识别 GT 质量问题的重要信号）；
- 嵌套结构（单据中的明细行列表）无处理策略，行为未定义。

### 2.5 合规项确认：大小写未归一化 ✓

`normalize()` 不涉及大小写转换，`LAU` vs `Lau` 会正确判为 MISMATCH，符合「不应当解决大小写错误」的规格。**该行为在重构中必须保留，并写入测试断言，防止后续"好心"加 `.lower()`。**

### 2.6 其他实现问题

- `match_score` 取值 `1.0/0.8/0.0`（`:181`）为拍脑袋常数，语义不明；
- `normalize(str(v))`（`:165-166`）对 `None`、数字、嵌套结构一律 `str()` 强转，行为粗糙（`None` → `"None"` 参与比较）；
- `RobustMatcher` 仅作分析附加（`result["robust_match"]`，`:569` 等），**不影响验收** —— 真正的验收判定在 `RobustJSONComparator` 中。

## 4. 需求规格：归一化规则（normalize）

设归一化函数 `N(text)`，两个字段值 `a, b` 满足 `N(a) == N(b)` 时判为**归一化一致**。规则必须精确、可测试、不超限：

### R-N1 全角 → 半角（规格内，必须做）

- **全角 ASCII 区**：U+FF01–U+FF5E 整体偏移映射（减 0xFEE0）→ 对应半角字符。覆盖全角字母、数字、符号（`Ａ→A`、`５→5`、`＄→$`、`＃→#` 等）；
- **全角空格** U+3000 → 半角空格；
- **货币宽度变体**：`￥`(U+FFE5) → `¥`(U+00A5)，`￡`(U+FFE1) → `£` 等；
- **中文标点 → 英文标点对照表**：`，：；？！（）【】""''、。` 等显式成对映射（用查表，不用猜测）。

> ⚠️ **禁用 `unicodedata.NFKC` 一刀切**：NFKC 会把 `™` 折叠为 `TM`、`①` 折叠为 `1` 等，而提取规则要求 `® ™` 等符号照抄保留（:31）—— 一刀切 NFKC 会把符号错误洗成一致。只使用上述受控映射。

### R-N2 标点相邻空格（规格内，必须做）

- 删除紧邻标点（半角与中文标点均含）**之后**的空白字符：`"LAU, LAI LI"` → `"LAU,LAI LI"`；
- 删除紧邻标点**之前**的空白：`"总价 :100"` → `"总价:100"`；
- 值的首尾空白 strip；
- **其余位置的空格一律保留**（英文姓名、地址内部空格承载语义，见 §2.2 反例）。

### R-N3 明确不做（规格外，做了即 bug）

- ❌ 大小写转换（`LAU` vs `Lau` → MISMATCH）；
- ❌ 删除货币符号或任何非空白字符（`¥5.83` vs `5.83` → MISMATCH）；
- ❌ 删除非标点相邻的内部空格（`LAU, LAI LI` vs `LAU,LAIL I` → MISMATCH）；
- ❌ 数字格式等价（`5.83` vs `5.830`、`1,000` vs `1000` → 默认 MISMATCH；如后续确有需要，单独立项并注明依据）。

## 5. 需求规格：逐字段比较与三级判定

替代整字典相等，对每个字段独立判定并聚合：

### R-C1 字段级三级判定

| 级别 | 定义 | 语义 |
|---|---|---|
| `STRICT` | 原始字符串完全相等 | 提取与标注完全一致 |
| `NORMALIZED` | `N(a) == N(b)` 但原始不等 | 格式噪声，非推理错误 |
| `MISMATCH` | 归一化后仍不等 | 真实差异（模型错 **或** GT 错，需交叉验证） |

另需区分两种结构级情形：`KEY_MISSING_IN_PRED`（模型漏字段）、`KEY_MISSING_IN_GT`（GT 缺字段 / 模型多输出）。

### R-C2 样本级聚合

样本判定 = 全字段判定的聚合：**全部 STRICT → STRICT；存在 NORMALIZED 但无 MISMATCH → NORMALIZED_MATCH；存在任一 MISMATCH → MISMATCH**。输出必须含逐字段明细（字段名、级别、预测值、GT 值），供诊断分析。

### R-C3 验收口径（主流程）

- `STRICT` 与 `NORMALIZED_MATCH` 均计为**验收通过**（格式噪声不应否决推理正确的样本），但结果中保留级别标记与原始响应，下游可按级别过滤；
- 3 并发抽卡选优：按「级别优先（STRICT > NORMALIZED > MISMATCH），同级按匹配字段数」排序取最优 —— 替代原拍脑袋的 `match_score`；
- 嵌套结构（明细行列表等）：逐层递归应用同一套规则，数组按位置对齐比较（首版不支持乱序对齐，留作扩展）。

## 6. 需求规格：GT 交叉验证分析

利用逐字段明细产出 GT 质量信号（离线分析，不影响主流程）：

- **字段级错误分布**：按字段聚合 MISMATCH 率 —— 某字段普遍不匹配且模式一致（如统一少一位、统一多后缀）→ 高度疑似 GT 系统性错误或 prompt 缺规则；
- **NORMALIZED 占比**：格式噪声率，反映标注风格不统一的严重程度，也是 prompt 标点规则调优的反馈；
- **KEY_MISSING 方向统计**：`MISSING_IN_GT` 集中出现 → GT 标注 schema 不全的证据；
- **逐样本三方视图**：对 MISMATCH 样本保留「模型 CoT 推理链 + 模型结论 + GT」，人工抽查时可借推理链判断错在模型还是 GT —— 这是 CoT 方案交叉验证价值落地的地方。

## 7. 验收指标（mock 测试断言）

1. **规格符合性**：为 §4 每条规则配正反例单测 —— 规格内变体必须判一致，规格外差异（大小写、缺符号、内部空格）必须判 MISMATCH；
2. **逐字段明细完整性**：任一 MISMATCH 样本的输出含全部字段的级别与原始值，无吞字段；
3. **判定一致性**：验收判定与诊断分析使用同一组件同一规则（消灭双实现）；
4. **回归保护**：`LAU` vs `Lau`、`¥5.83` vs `5.83`、`LAU, LAI LI` vs `LAU,LAIL I` 三个反例固化进测试集，永久防回归。
