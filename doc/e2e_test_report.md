二、EMPTY_RESPONSE 问题诊断 — 核心根因

### 2.1 数据特征

| 维度  | 统计  |
| --- | --- |
| EMPTY_RESPONSE 数量 | **13 / 30 = 43.3%** |
| `finish_reason` | 全部为 `length` |
| `completion_tokens` | 全部为 **32768**（API 上限） |
| `content` | 全部为 `null` |
| `reasoning_content` 长度 | 48k–67k 字符 |
| 耗时（RTT） | 230s–316s |

### 2.2 根因定位

**所有 13 个 EMPTY_RESPONSE 具有完全一致的模式：**

```
API 调用
  → enable_thinking=true
  → 模型开始在 reasoning_content 中思考
  → thinking 内容持续增长（48k-67k 字符）
  → 达到 max_tokens=32768 上限
  → finish_reason=length
  → content=null（从未输出最终 JSON）
```

**这不是网络问题。** 网络层面表现正常：

- RATE_LIMITED 仅 4 次（7%）
- 成功请求 RTT 中位数 ~10s，没有超时
- 所有 EMPTY_RESPONSE 都有完整的 thinking 内容（只是太长）

### 2.3 模型行为分析

从 `reasoning_content` 采样可见典型的**过度推理循环**：

```
"让我们再看一眼，那个字其实是"元"。
让我们再看一眼，那个字其实是"元"。
让我们再看一眼，那个字其实是"元"。
...（重复数十次）
```

- 模型在 thinking 阶段进入"反复自我验证-否定-再验证"的死循环
- 对模糊字段（手写体、印刷体混杂）尤其容易触发
- 63k+ 字符的 thinking 中只有少量有效推理，大部分是重复确认

### 2.4 重试无效

- sample_8 和 sample_4 各重试 3 次
- sample_9 重试 2 次
- 每次都以相同方式失败（thinking 耗尽 token）
- 说明这是**确定性失败**，不是随机网络波动

### 2.5 风险影响

| 影响  | 评估  |
| --- | --- |
| 成功率 | 被 EMPTY_RESPONSE 从预期 >50% 拉低至 26.7% |
| 吞吐量 | 每个空响应浪费 4-5 分钟，13 个共计近 1 小时 |
| API 费用 | 空响应的 token 消耗可能仍然计费（thinking 内容实际产生） |

### 2.6 建议方向

1. **降低 `max_tokens` 到 4096-8192**，强制模型在 thinking 上减少消耗，腾出 space 给 content
2. **Prompt 层面限制 thinking 长度**：添加"请简洁推理，10 步以内完成，不要重复确认"
3. **对于字段 > 15 的复杂样本**，考虑拆分或改用非 thinking 模式
4. 当前 `max_tokens=32768` 的默认值对 thinking 模型有害无益

**观察**：QPM 控制有效。平均 38 QPM 低于 50 上限，16% 的 limiter 等待时间在正常范围。

### 3.3 请求耗时分布

| 分位  | OK 请求（40次） | EMPTY_RESPONSE（13次） |
| --- | --- | --- |
| **p50** | **~10s** | **~248s** |
| p95 | ~30s | ~259s |
| p99 | ~31s | ~316s |
| min | ~4s | ~230s |
| max | ~31s | ~316s |

**核心结论**：

- OK 请求延迟分布健康：**4–30s，中位数 ~10s**
- EMPTY_RESPONSE 全部卡在 **230–316s**（卡在 API 的 thinking 超时上）
- 整体 p95=251s 被空响应拉高了 **25 倍**
- 没有中间状态的请求（如 100s 返回的），分布呈现**双峰特征**

### 3.4 重试放大

| 指标  | 值   |
| --- | --- |
| total_http_requests | 57  |
| amplification | **1.9x** |
| quota_initial | 30  |
| quota_retry_quality | 23（占 retry 的 85%） |
| quota_retry_network | 4（15%） |

**观察**：1.9x 放大系数正常。retry 的主体是 quality retry（MISMATCH 触发），network retry 仅 4 次（对应 RATE_LIMITED）。

3.5 时间相位分析（瓶颈在哪）

| 阶段  | 总耗时（秒） | 占比  |
| --- | --- | --- |
| **rtt**（API 响应等待） | **3728** | **83.3%** |
| wait_limiter（QPM 等待） | 724 | 16.2% |
| backoff（退避） | 22  | 0.5% |
| wait_slot（槽位等待） | 0   | 0%  |
| **总计** | **4474** | **100%** |

**结论**：RTT 是绝对瓶颈。提高并发不会显著加速——30 个请求花了 3728 秒在等 API 响应。瓶颈在 API 本身的响应速度。

### 3.6 Mock API 建模建议

基于 57 次请求的实测数据，以下为 mock API 参数：

#### 延迟分布（混合双峰模型）

```
RTT ≈ 70% LogNormal(μ=2.3, σ=0.6) + 30% 固定 250s
```

- **OK 模式**（占 ~70%）：`LogNormal(μ=2.3, σ=0.6)`，复现 4–30s 分布，中位数 ~10s
- **空响应模式**（占 ~30%）：固定延迟 `250s`，复现 230–316s 的空响应超时

#### 错误率配置

| 类型  | 概率  | 说明  |
| --- | --- | --- |
| OK  | ~70% | 正常返回 |
| EMPTY_RESPONSE | ~23% | thinking 耗尽 token，返回空内容 |
| RATE_LIMITED | ~7% | 仅在 QPM > 50 时触发（早期突发） |

#### 限流策略

```
滑动窗口：60s
上限：50 req/min
超限行为：随机延迟 0.1–0.5s 后重试
超限率：~7%（早期阶段偏高，平稳后接近 0）
```

#### 重试行为

```
第一次返回 EMPTY_RESPONSE → quality retry（最多 3 次）
第一次返回 RATE_LIMITED  → network retry（最多 5 次）
quality retry 第二次和第三次行为相同（确定性失败，非随机）
backoff: exponential(1s, max 10s)
```

#### 并发模拟

```
max_concurrent: 22（实际峰值，非配置值）
每样本并发: 1（串行重试）
新样本间隔: ~3s（前 10 秒 9 个样本的发射频率）
```

## 四、实际耗时 vs 串行估算

### 4.1 实测耗时

| 指标  | 值   |
| --- | --- |
| 第一条请求 ts | 5609274.50 |
| 最后一条请求 ts | 5609645.62 |
| **总耗时** | **371.12 秒 = 6.19 分钟** |
| 样本数 | 30  |
| 总请求数 | 57  |

### 4.2 串行估算

按实测 RTT 分布推算串行耗时：

| 请求类型 | 数量  | 平均 RTT | 串行耗时 |
| --- | --- | --- | --- |
| OK 请求 | 40  | ~10s | ~400s（6.7 分钟） |
| EMPTY_RESPONSE | 13  | ~250s | ~3250s（54.2 分钟） |
| **合计** | **53** | —   | **~3650s（60.8 分钟）** |

### 4.3 加速比

| 模式  | 耗时  | 说明  |
| --- | --- | --- |
| **并行（实际）** | **6.2 分钟** | 30 样本，57 次请求 |
| **串行（估算）** | **~61 分钟** | 按实测 RTT 分布 |
| **加速比** | **9.8x** | 节省 54.6 分钟 |

### 4.4 核心观察

1. **你的体感是对的** — 从"接近一小时"压缩到"6 分钟"，**9.8 倍加速**
2. **加速主要来自空响应超时并行化** — 13 个 EMPTY_RESPONSE 串行要浪费 54 分钟，现在被并发窗口摊平到 6 分钟内
3. **解决空响应后加速比会下降** — 如果 EMPTY_RESPONSE 全部变 OK（RTT 从 250s 降到 10s）：
  - 串行耗时：53 × 10s ≈ **9 分钟**
  - 并行耗时：≈ **6 分钟**
  - 加速比：从 **9.8x 降到 1.5x**

**结论**：当前阶段并行的核心价值是"长尾超时场景的摊平"，解决了空响应问题后，并行对总耗时的边际收益会降低（因为模型 API 本身响应就慢，10s 是硬约束）。

## 五、总结 & 优先级

| 优先级 | 问题  | 影响  | 处理  |
| --- | --- | --- | --- |
| **P0** | Thinking 模式下 `max_tokens` 耗尽致 `content=null` | 43.3% 样本直接报废 | 降低 max_tokens + 优化 prompt 限制 thinking 长度 |
| P1  | MISMATCH 质量 9/30（30%） | 影响内容正确性 | 优化 CoT prompt，属于正常迭代 |
| P2  | 并发只到 22/30（73%） | 大样本时才会改善 | 多给样本自然解决，非阻塞 |
| P3  | RATE_LIMITED 占 7% | 少量  | 微调 QPM 限流参数 |

### 一句话结论

当前 V3 框架的**并发和限流部分工作正常**（峰值并发 22，放大系数 1.9，limiter 仅 16% 开销），但 **43% 的样本因 thinking 模式下 token 耗尽而空响应**，这是下阶段必须解决的最致命问题。
